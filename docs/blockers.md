# Blockers: the AgentPulse contract (O1)

Status, 2026-11-22: **decided and agreed with AgentPulse. Its milestone 40 builds it under `/v1/`. Taskify's side is task group AP in [r2-agents.md](archive/r2-agents.md), done: the client and the mock follow the agreed contract below, including the details AgentPulse confirmed afterwards (AP-12). Waiting on AgentPulse to ship slices 40a to 40d, after which task M0-07 checks Taskify against it.**

## Background

Taskify's integration was designed from the owner's description of AgentPulse ([architecture.md](architecture.md) section 5.5) and built against a mock ([tests/mockagentpulse](../tests/mockagentpulse/server.go)). The AgentPulse repository (milestone 39d, branch `feature/m39d-real-clients`) was then checked against that description. It does not match:

- AgentPulse is one workspace per deployment, with no tenants.
- Events have no recipient. Channels and their targets are configured on the server, and rules choose among them.
- Its `POST /notify` is a plain send (`agent`, `title`, `message`, `emailRecipients`, Slack/Teams webhook URLs). It skips rules, deduplication, budgets and digests.
- The attention features (rules, dedup, budget, digest, inbox, feedback, learning) work only on `POST /api/events`, authenticated with `X-API-Key`.
- Digests and inbox read state cover the whole workspace, not one user.
- Nothing calls back to a client when someone clicks an action. The only webhook targets are Slack and Teams incoming-webhook URLs.
- Learning suggestions are generated by AgentPulse from feedback. An app cannot submit one.
- `GET /api/analytics` has no dismiss or mute ratios by event type or label.

## Decision (owner, 2026-11-22): option B

**AgentPulse is extended with the API Taskify was designed for.** Taskify keeps its design. Its mock AgentPulse becomes the specification of what AgentPulse must add, and Taskify work continues against the mock, including M10, M11 and M14-06. Final sign-off of M2, M3, M10, M11 and M14's notification feed still waits until the real endpoints exist and Taskify's client passes against them (task M0-07).

Rejected: C (Taskify owns recipients, feed, action links and per-user digests, and uses AgentPulse only for attention decisions). Also rejected: A (adapt Taskify wholesale).

## What AgentPulse needs to add

This is the specification to hand to the AgentPulse repository. JSON fields are camelCase. Taskify sends `Authorization: Bearer <key>` today. If AgentPulse keeps `X-API-Key`, Taskify changes one header in `internal/agentpulse/client.go`. Say which.

### R1. Multi-tenancy

Every call below carries a `tenantId` (string, up to 64 characters). Rules, preferences, budgets, digests, feedback, learning and feeds are kept separately per tenant. One AgentPulse deployment serves many Taskify tenants.

### R2. `POST /notify`: per-recipient notifications through the attention pipeline

A new or extended endpoint. Unlike today's plain send, it goes through rules, dedup, preferences, budget and digest, keyed on `(tenantId, userId)`.

| Field | Type | Notes |
| --- | --- | --- |
| `idempotencyKey` | string, required | Up to 320 characters. Any printable ASCII. A repeat returns the first result. |
| `tenantId` | string, required | |
| `userId` | string, required | The recipient. Budget and preferences are kept per user. |
| `source` | string | `taskify` |
| `eventType` | string, required | e.g. `task.assigned`, `task.escalated`, `agent.approval_requested` |
| `title` | string, required | One line |
| `body` | string, required | |
| `channels` | string array | Any of `slack`, `email`, `in_app`, `webhook`, `digest`. `digest` alone means deliver only in the user's digest. |
| `priorityHint` | string | `critical`, `high`, `medium`, `low`. An input to rules, not a guarantee. |
| `payload` | object | Free-form, stored, matchable by rules. Reserved keys below. |

Reserved `payload` keys:

- `bypassDigest: true` means deliver now, never hold for a digest.
- `digestSummary` is the text the digest shows for this item.
- `actionUrls` is a map from action name to URL, for example `{"acknowledge": "...", "snooze_2h": "...", "approve": "...", "reject": "...", "unblock": "...", "view": "..."}`.
- `actionLabels` is an optional map from action name to button text.

Responses:

- `202 {"id": "<notificationId>", "duplicate": false}`
- `200 {"id": "<first id>", "duplicate": true}` for a repeated key
- `400 {"error": "..."}` for an invalid body
- `401` for a bad key
- `429` or `503` with an optional `Retry-After`. Taskify retries these with backoff.

How a user is reached on Slack or email (a user directory, or a mapping from `(tenantId, userId)` to addresses) is AgentPulse's design. Taskify sends user IDs only.

### R3. Action callbacks to Taskify

When a person clicks an action in any channel, AgentPulse calls Taskify:

- `POST {taskifyBaseUrl}/api/v1/webhooks/agentpulse`, configured per deployment or per tenant.
- Headers: `X-AgentPulse-Timestamp: <unix seconds>`, and `X-AgentPulse-Signature: sha256=<hex HMAC-SHA256 of "<timestamp>.<raw body>">`, using a shared secret.
- Body: `{"action": "complete|snooze|unblock|approve|reject", "tenantId", "userId", "taskId", "jobId" (approve and reject), "notificationId", "duration" (snooze, e.g. "2h")}`.
- Taskify answers `200 {"status": "applied|duplicate"}`. A byte-identical replay is treated as a duplicate. Timestamps older than 5 minutes are rejected.

### R4. `POST /feedback`

`{"notificationId", "tenantId", "userId", "signal": "acted|dismissed|snoozed|muted", "snoozeDuration"?, "taskId"?}`, answered with `202 {"status": "recorded"}`. Feedback is recorded per user and feeds learning. This differs from today's `{eventId, action}`.

### R5. Rules API, per tenant

- `POST /rules` with `{"tenantId", "name", "matchAny": [{"eventTypes": [...], "payloadMatch": {...}}], "channels": [...], "bypassDigest"?}`, answered with `201 {"id"}`.
- `GET /rules?tenantId=` returns `{"rules": [...]}`.
- `matchAny` means the rule applies when any entry matches. If AgentPulse keeps all-of conditions only, Taskify can send one rule per entry. Say which.

### R6. Learning suggestions submitted by an app

- `POST /learning/suggestions` with `{"tenantId", "ruleId" or "eventPattern", "currentAdjustment", "proposedAdjustment" (between -20 and 20), "signalCount" (at least 5 signals from at least 2 users), "rationale"}`, answered with `201`. It is stored as `PENDING_APPROVAL` and changes nothing until an admin decides.
- `GET /learning/suggestions?tenantId=` returns `{"suggestions": [{"id", "status", "suggestion": {...}}]}`.
- `POST /learning/suggestions/{id}/decision` with `{"decision": "approve|reject", "decidedBy"}` returns `200` with the suggestion, or `409` if already decided.

AgentPulse's own generated suggestions can keep living alongside these.

### R7. Feedback analytics (for Taskify's M11)

`GET /analytics/feedback?tenantId=&since=<RFC 3339>` returns counts per `eventType` and per payload label:

```json
{"since": "...", "groups": [
  {"eventType": "task.updated", "label": "docs", "delivered": 40, "acted": 3, "dismissed": 30, "muted": 2, "snoozed": 1, "distinctUsers": 6}
]}
```

`label` is each value of `payload.labels`. A notification with no labels is counted under `label: null`.

### R8. Per-user in-app feed (for Taskify's M14-06)

`GET /internal/v1/tenants/{tenantId}/users/{userId}/in-app-feed?limit=&cursor=` returns `{"notifications": [{"id", "eventType", "title", "body", "createdAt", "payload": {...}}], "nextCursor"}`, newest first. Taskify keeps read state itself.

### R9. Health

`GET /healthz`. If AgentPulse keeps `/health`, Taskify changes its probe. Say which.

## Agreed with AgentPulse (2026-11-22)

AgentPulse builds R1 to R9 in its milestone 40, in four slices. Its plan is in its own repository, at `docs/milestones/tenant-api-plan.md`.

| Slice | Covers |
| --- | --- |
| 40a | R1 tenants, contacts, R2 `/v1/notify`, R5 `/v1/rules` with `matchAny`, R9 `/healthz`, Bearer auth |
| 40b | R3 action callbacks, R4 `/v1/feedback` |
| 40c | R6 learning suggestions, R7 feedback analytics |
| 40d | R8 in-app feed, Slack direct messages |

Changes to the specification above:

- **Paths.** Every endpoint is under `/v1/`: `/v1/notify`, `/v1/feedback`, `/v1/rules`, `/v1/learning/...`, `/v1/analytics/feedback`, and `/v1/tenants/{t}/users/{u}/in-app-feed`. `/healthz` stays. AgentPulse accepts `Authorization: Bearer` as well as `X-API-Key`.
- **Tenant IDs** must match `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`. They are compared case-sensitively and never trimmed, and `default` is refused. Taskify enforces the same rule (AP-04).
- **Contacts.** Taskify calls `PUT /v1/tenants/{t}/users/{u}/contact` with `{email, slackUserId, phone}`.
  - It is a full replace: a field that is `null` or left out is cleared, and a contact with all three empty is deleted.
  - Sending the same body again changes nothing.
  - A user with no contact gets in-app and digest delivery only.
  - Taskify adds `PUT /api/v1/me/contact` for users to set their own contact (AP-05).
- **Rules.** `matchAny` is supported natively.
  - A rule may set `attentionClass` (`critical`, `standard`, `background`).
  - A critical rule needs a real condition in every entry.
  - AgentPulse's own locked critical rules run first, then the tenant's rules, then a default of `standard`.
  - Taskify's default rule makes p1_critical tasks, manual blocks, and `task.escalated` critical (AP-03).
- **Digest and priority.** `bypassDigest` keeps an item out of the digest, but budget and quiet hours still apply, and it never makes an item critical. `priorityHint` is only an input to rules.
- **Idempotency.** The key is stored as sent: up to 320 printable ASCII characters, unique per tenant.
- **Actions.**
  - AgentPulse makes its own signed links for callback actions. Only `view` is used as sent.
  - A click opens a confirmation page, and the action runs when the button is pressed.
  - Each link works once and expires after 7 days. Without AgentPulse's `ACTIONS_PUBLIC_BASE_URL`, messages carry only the view link.
  - The keys are fixed:

    | `actionUrls` key | Callback `action` | IDs read from the payload | Default button text |
    | --- | --- | --- | --- |
    | `complete` | `complete` | `taskId` | Mark done |
    | `snooze_2h` | `snooze`, with `duration: "2h"` | `taskId` | Snooze 2h |
    | `approve` | `approve` | `jobId` | Approve |
    | `reject` | `reject` | `jobId` | Reject |
    | `unblock` | `unblock` | `taskId` | Unblock and set In Progress |
    | `view` | none, a plain link | | View |

  - `payload.actionLabels` overrides the button text.
  - From 40b, an unknown key or a missing ID is refused with a 400, so Taskify replaces `acknowledge` with `complete` first (AP-02).
  - A notification that is not about a task, such as `digest.morning_brief`, carries only `view`.
- **Callbacks** go through AgentPulse's delivery queue, which retries them.
  - The body carries `callbackId`: `cb-` plus 32 hex characters, the same on every retry of one click, while the timestamp and signature are new each time.
  - Taskify deduplicates on `(tenantId, callbackId)` (AP-06).
  - Taskify's callback URL must be https and on AgentPulse's allow-list.
- **Learning.** `proposedAdjustment` is AgentPulse's heuristic score shift for that scope, in the same unit as its own learned adjustments.
- **Slack.** One Slack workspace per AgentPulse deployment for now. Per-tenant workspaces come in a later AgentPulse milestone.

Confirmed by AgentPulse later on 2026-11-22 (Taskify's AP-12):

- **Feedback without a notification.** In R4, `notificationId` is optional, and an empty string means the same as absent. At least one of `notificationId` and `taskId` is required.
  - With no notification, AgentPulse links the feedback to that user's latest notification whose `payload.taskId` matches, and counts it in learning and analytics under that notification's event type and labels. If there is none, the feedback is stored but not counted.
  - Taskify leaves `notificationId` out when it has none, rather than sending `""`, and always sends `taskId`.
- **Tenant scoping.** Every `/v1/` call that names an object by ID (rules, learning suggestions, notifications) requires `tenantId`, answering `400` without it, and another tenant's object answers `404`, the same as an unknown ID.
  - The R6 decision body is `{"tenantId", "decision", "decidedBy"}`, so Taskify's admin proxy can decide only the caller's tenant's suggestions.
  - A feedback `notificationId` that the tenant does not hold answers `404`.
- **Contact formats,** exactly as AgentPulse validates them, and Taskify validates the same:
  - `email`: a plain address of at most 254 characters, with no display name;
  - `slackUserId`: `^[UW][A-Z0-9]+$`, at most 32 characters;
  - `phone`: `^\+[1-9][0-9]{1,14}$`.
  - One bad field refuses the whole PUT with a `400` naming it. Taskify's relay treats that as permanent: the row goes to dead letter with the reason, without a retry.

## Learning and analytics as Taskify's mock serves them (M11, for 40c)

R6 and R7 leave some details open. Taskify's M11 fixed them in the mock as follows; AgentPulse should confirm them, or say what differs, before 40c ships.

- **`eventPattern`** is `{"eventType", "label"}`, the same scope as an R7 group: one event type and one value of `payload.labels`, with `"label": null` for notifications that carry no label.
- **R6 validation.** A submitted suggestion needs a valid `tenantId`; `ruleId` or `eventPattern`; `currentAdjustment` and `proposedAdjustment`, numbers within -20 and 20; a `signalCount` of at least 5; and a `rationale`. Anything else is a `400` naming the field. The `201` body is the stored suggestion, `{"id", "status": "PENDING_APPROVAL", "suggestion"}`.
- **R7 counting.** `since` is RFC 3339 and the response echoes it. `delivered` counts the tenant's notifications accepted at or after `since`, once under each of their labels. A feedback signal received at or after `since` counts under the notification it names, or, without one, the user's latest notification about its task (AP-12), once under each of that notification's labels. `distinctUsers` is how many users the group's counted signals came from. A group with deliveries and no signals is listed.

Requests to AgentPulse:

- **An idempotency key for R6.** `POST /v1/learning/suggestions` has none. Taskify submits through its outbox, which retries after a timeout, so a lost response stores the suggestion twice. Taskify asks for an `idempotencyKey`, unique per tenant, as on `/v1/notify`. Until then, a duplicate pending suggestion is possible, and an admin rejects one of the two.
- **The current adjustment.** Taskify has no read of the adjustment in force for a scope. It sends as `currentAdjustment` the `proposedAdjustment` of the latest approved suggestion for the same `eventPattern` in `GET /v1/learning/suggestions`, or 0. AgentPulse should either expose the current adjustment per scope, for example in R7's groups, or confirm that it ignores `currentAdjustment` and applies `proposedAdjustment` as the new value.
