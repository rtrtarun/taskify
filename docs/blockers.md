# Blockers: the AgentPulse contract (O1)

Status, 2026-11-22: **decided, waiting on AgentPulse.**

## Background

Taskify's integration was designed from the owner's description of AgentPulse ([architecture.md](architecture.md) section 5.5) and built against a mock ([tests/mockagentpulse](../tests/mockagentpulse/server.go)). The AgentPulse repository (milestone 39d, branch `feature/m39d-real-clients`) was then checked against that description. It does not match:

- AgentPulse is one workspace per deployment, with no tenants.
- Events have no recipient. Channels and their targets are configured on the server, and rules choose among them.
- Its `POST /notify` is a plain send (`agent`, `title`, `message`, `emailRecipients`, Slack/Teams webhook URLs). It skips rules, deduplication, budgets and digests.
- The attention features (rules, dedup, budget, digest, inbox, feedback, learning) work only on `POST /api/events`, authenticated with `X-API-Key`.
- Digests and inbox read state cover the whole workspace, not one user.
- Nothing calls back to a client when someone clicks an action. The only webhook targets are Slack and Teams incoming-webhook URLs.
- Learning suggestions are generated by AgentPulse from feedback. An app cannot submit one.
- `GET /api/analytics` has no dismiss or mute ratios by event type or label.

## Decision (owner, 2026-11-22): option B

**AgentPulse is extended with the API Taskify was designed for.** Taskify keeps its design. Its mock AgentPulse becomes the specification of what AgentPulse must add, and Taskify work continues against the mock, including M10, M11 and M14-06. Final sign-off of M2, M3, M10, M11 and M14's notification feed still waits until the real endpoints exist and Taskify's client passes against them (task M0-07).

Rejected: C (Taskify owns recipients, feed, action links and per-user digests, and uses AgentPulse only for attention decisions). Also rejected: A (adapt Taskify wholesale).

## What AgentPulse needs to add

This is the specification to hand to the AgentPulse repository. JSON fields are camelCase. Taskify sends `Authorization: Bearer <key>` today. If AgentPulse keeps `X-API-Key`, Taskify changes one header in `internal/agentpulse/client.go`. Say which.

### R1. Multi-tenancy

Every call below carries a `tenantId` (string, up to 64 characters). Rules, preferences, budgets, digests, feedback, learning and feeds are kept separately per tenant. One AgentPulse deployment serves many Taskify tenants.

### R2. `POST /notify`: per-recipient notifications through the attention pipeline

A new or extended endpoint. Unlike today's plain send, it goes through rules, dedup, preferences, budget and digest, keyed on `(tenantId, userId)`.

| Field | Type | Notes |
| --- | --- | --- |
| `idempotencyKey` | string, required | Up to 320 characters. Any printable ASCII. A repeat returns the first result. |
| `tenantId` | string, required | |
| `userId` | string, required | The recipient. Budget and preferences are kept per user. |
| `source` | string | `taskify` |
| `eventType` | string, required | e.g. `task.assigned`, `task.escalated`, `agent.approval_requested` |
| `title` | string, required | One line |
| `body` | string, required | |
| `channels` | string array | Any of `slack`, `email`, `in_app`, `webhook`, `digest`. `digest` alone means deliver only in the user's digest. |
| `priorityHint` | string | `critical`, `high`, `medium`, `low`. An input to rules, not a guarantee. |
| `payload` | object | Free-form, stored, matchable by rules. Reserved keys below. |

Reserved `payload` keys:

- `bypassDigest: true` means deliver now, never hold for a digest.
- `digestSummary` is the text the digest shows for this item.
- `actionUrls` is a map from action name to URL, for example `{"acknowledge": "...", "snooze_2h": "...", "approve": "...", "reject": "...", "unblock": "...", "view": "..."}`.
- `actionLabels` is an optional map from action name to button text.

Responses:

- `202 {"id": "<notificationId>", "duplicate": false}`
- `200 {"id": "<first id>", "duplicate": true}` for a repeated key
- `400 {"error": "..."}` for an invalid body
- `401` for a bad key
- `429` or `503` with an optional `Retry-After`. Taskify retries these with backoff.

How a user is reached on Slack or email (a user directory, or a mapping from `(tenantId, userId)` to addresses) is AgentPulse's design. Taskify sends user IDs only.

### R3. Action callbacks to Taskify

When a person clicks an action in any channel, AgentPulse calls Taskify:

- `POST {taskifyBaseUrl}/api/v1/webhooks/agentpulse`, configured per deployment or per tenant.
- Headers: `X-AgentPulse-Timestamp: <unix seconds>`, and `X-AgentPulse-Signature: sha256=<hex HMAC-SHA256 of "<timestamp>.<raw body>">`, using a shared secret.
- Body: `{"action": "complete|snooze|unblock|approve|reject", "tenantId", "userId", "taskId", "jobId" (approve and reject), "notificationId", "duration" (snooze, e.g. "2h")}`.
- Taskify answers `200 {"status": "applied|duplicate"}`. A byte-identical replay is treated as a duplicate. Timestamps older than 5 minutes are rejected.

### R4. `POST /feedback`

`{"notificationId", "tenantId", "userId", "signal": "acted|dismissed|snoozed|muted", "snoozeDuration"?, "taskId"?}`, answered with `202 {"status": "recorded"}`. Feedback is recorded per user and feeds learning. This differs from today's `{eventId, action}`.

### R5. Rules API, per tenant

- `POST /rules` with `{"tenantId", "name", "matchAny": [{"eventTypes": [...], "payloadMatch": {...}}], "channels": [...], "bypassDigest"?}`, answered with `201 {"id"}`.
- `GET /rules?tenantId=` returns `{"rules": [...]}`.
- `matchAny` means the rule applies when any entry matches. If AgentPulse keeps all-of conditions only, Taskify can send one rule per entry. Say which.

### R6. Learning suggestions submitted by an app

- `POST /learning/suggestions` with `{"tenantId", "ruleId" or "eventPattern", "currentAdjustment", "proposedAdjustment" (between -20 and 20), "signalCount" (at least 5 signals from at least 2 users), "rationale"}`, answered with `201`. It is stored as `PENDING_APPROVAL` and changes nothing until an admin decides.
- `GET /learning/suggestions?tenantId=` returns `{"suggestions": [{"id", "status", "suggestion": {...}}]}`.
- `POST /learning/suggestions/{id}/decision` with `{"decision": "approve|reject", "decidedBy"}` returns `200` with the suggestion, or `409` if already decided.

AgentPulse's own generated suggestions can keep living alongside these.

### R7. Feedback analytics (for Taskify's M11)

`GET /analytics/feedback?tenantId=&since=<RFC 3339>` returns counts per `eventType` and per payload label:

```json
{"since": "...", "groups": [
  {"eventType": "task.updated", "label": "docs", "delivered": 40, "acted": 3, "dismissed": 30, "muted": 2, "snoozed": 1, "distinctUsers": 6}
]}
```

`label` is each value of `payload.labels`. A notification with no labels is counted under `label: null`.

### R8. Per-user in-app feed (for Taskify's M14-06)

`GET /internal/v1/tenants/{tenantId}/users/{userId}/in-app-feed?limit=&cursor=` returns `{"notifications": [{"id", "eventType", "title", "body", "createdAt", "payload": {...}}], "nextCursor"}`, newest first. Taskify keeps read state itself.

### R9. Health

`GET /healthz`. If AgentPulse keeps `/health`, Taskify changes its probe. Say which.

## Open questions for the AgentPulse side

1. Is `Authorization: Bearer` acceptable, or does Taskify switch to `X-API-Key`?
2. `matchAny`, or one rule per condition (R5)?
3. `/healthz` or `/health` (R9)?
4. How many milestones does AgentPulse need for R1 to R8? Which come first? Taskify needs R2 to R5 for its R1 sign-off, R6 and R7 for M11, and R8 for M14-06.

## What happens in Taskify meanwhile

- Work continues against the mock. The mock is kept in line with this spec, and any change to the spec changes the mock in the same commit.
- When AgentPulse ships these endpoints, task M0-07 runs Taskify's client and webhook tests against a real AgentPulse. M2, M3, M10, M11 and M14-06 are signed off then.
